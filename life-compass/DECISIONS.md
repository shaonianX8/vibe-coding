# 重大设计决策

每条记录：决定了什么、为什么、付出的代价、什么情况下应该重新考虑。

## D1 技术栈：Next.js + Supabase + Vercel

- **决定**：Next.js 16（App Router，TypeScript）做成可安装到主屏幕的网页应用；Supabase 提供 PostgreSQL、登录和定时任务；Vercel 托管。
- **为什么**：一个代码库同时覆盖页面和服务端；三者都有免费套餐；PostgreSQL 和标准网页推送不绑定供应商，以后可以整体迁移。
- **代价**：iPhone 网页推送要求先添加到主屏幕；国内访问 Vercel 默认域名不稳定（见 DEPLOYMENT.md）。
- **重新考虑**：如果国内访问长期不可用，迁移到备案后的国内云服务。

## D2 手机只和应用服务器通信

- **决定**：所有数据库读写在服务端完成，浏览器里没有任何密钥，也不直接连接 Supabase 或 AI 服务。
- **为什么**：只有一个域名需要能访问；密钥不出服务器；权限检查集中。
- **代价**：每次操作多一跳服务器，延迟略高。把 Vercel 函数区域和 Supabase 放在同一地区可以抵消大部分。

## D3 登录用邮箱和密码，不用邮件魔法链接

- **为什么**：iPhone 主屏幕应用和 Safari 的登录状态是分开的，点邮件里的链接会在 Safari 里登录，主屏幕应用仍然是未登录；另外 Supabase 默认邮件服务发到部分国内邮箱容易延迟或进垃圾箱。密码可以存进 iPhone 钥匙串。
- **代价**：需要自己保管一个强密码。

## D4 两道门：关闭注册 + 邮箱允许名单

- **决定**：账户只在 Supabase 后台创建，并关闭公开注册；应用再检查 `ALLOWED_EMAILS`。允许名单为空时任何人都进不来。
- **为什么**：这是私人系统，默认拒绝比默认开放安全。

## D5 定时提醒用 Supabase Cron，不用 Vercel Cron

- **为什么**：Vercel 免费套餐的定时任务每天只能运行一次，且时间精度在一小时内浮动，无法支持用户自定义提醒时间。Supabase 的 pg_cron 每 10 分钟可靠运行，通过 pg_net 调用应用，密钥存在 Vault 里。
- **已验证**：本地完整链路（数据库定时任务 → HTTP 请求 → 应用返回 200）。

## D6 提醒宁可漏发，不可重复

- **决定**：每条提醒用唯一键抢占发送权；只重试明确失败的发送（网络错误、429、5xx），状态为发送中的不重试。
- **为什么**：重复提醒会快速消耗注意力和信任，比偶尔漏一次的伤害大。
- **代价**：如果服务器恰好在发送过程中崩溃，那天的提醒可能丢失。

## D7 规则优先，AI 可选

- **决定**：下一步建议、预警、统计全部由确定性规则完成，并有单元测试；AI 只在用户点击时细化建议。
- **为什么**：规则可测试、可解释、零成本、不会失联；AI 适合解释，不适合计算。也符合「不能用复杂分析代替解决现实问题」。

## D8 AI 用官方 Anthropic SDK，接口可替换

- **决定**：默认 `claude-opus-5-5`，结构化输出，`effort: medium`，开启服务端备用模型，24 小时调用上限默认 20 次。业务逻辑只依赖 `AiProvider` 接口。
- **未验证**：开发环境里没有 API 密钥，真实 API 调用没有跑过，只用测试模型验证了全部流程。配置密钥后请先点一次「让 AI 细化这条建议」确认。

## D9 仓库里不放任何个人敏感背景

- **为什么**：仓库目前是公开的。即使改为私有，代码仓库也不是存放健康、债务、关系信息的合适地方。
- **做法**：仓库只放方向性模板；个人背景、行为假设、现实约束只在应用里录入，存进受 RLS 保护的数据库。

## D10 不自动导入 ChatGPT 历史

- **为什么**：历史账户有多人使用，自动导入可能把别人的健康、财务、家庭信息混进来，而且一旦混入很难清理干净。V0 不提供导入。

## D11 战略修改必须写原因，AI 提案在数据库层面无法生效

- **为什么**：重大方向变化应当是用户自己的决定。约束写在数据库里，而不只是写在代码里，即使以后代码出错，AI 也无法改写生效战略。

## D12 断网时把未提交内容存在本机，不做离线同步

- **为什么**：完整的离线同步队列复杂且容易出现冲突。每天的记录只需要一分钟，断网时保住已输入的内容、联网后再点一次提交，已经覆盖主要场景。

## D13 模式只能手动切换

- **为什么**：系统可以建议进入紧急或恢复模式，但长期改变生活状态的判断属于用户。

## D14 不做连续打卡天数和游戏化激励

- **为什么**：打卡连续天数会让休息、生病、旅行变成「失败」，也会诱导无意义的点击。成功的衡量是关键行动是否改善，以及工具负担是否下降。
- **做法**：从第一天记录计划耗时、记录耗时、提醒被点开率，作为工具自检的基线，每四周复查。

## D15 V0 比清单多做了几项

在 V0 清单之外，提前做了：云端定时提醒、基础规则预警、数据导出与删除、部署助手。

- **为什么**：没有定时提醒，每日闭环无法在真实生活中运转；预警和导出删除的代码量小，并且是验收中特别测试和隐私要求的一部分；部署助手让不写代码的用户可以安全生成密钥。
- **刻意没做**：经济记录、周复盘页面、月季年复盘、五种资本趋势、决策复盘、健康计划导入、图表与仪表盘。

## D16 项目放在 `life-compass/` 子目录

- **为什么**：仓库名 `vibe-coding` 更像一个通用实验仓库，放在子目录避免和以后的其他项目混在一起。部署时在 Vercel 设置 Root Directory 即可。
